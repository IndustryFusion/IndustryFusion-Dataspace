# Design

## Context

See proposal.md - Why. The repository holds only `README.md`, `manifest.md`,
`architecture.md` and `LICENSE`. `architecture.md` describes components and files
that are not in the repository yet, such as `management/api/` and `keycloak.md`.
There is no CI. The plan was posted on issue #2.

The setup follows the one in IndustryFusion/XANA-AI-PDT, so both repositories work
the same way. Project-specific content is written for this repository.

## Goals / Non-Goals

**Goals:**

- Use OpenSpec's native schema, commands and skills, and add only configuration,
  instructions and documentation around them.
- Keep specifications agent-independent. Agent-specific files are generated by
  `openspec init` and point at shared instructions.
- Bring the differences between the project documents to maintainers instead of
  settling them in the project context.

**Non-Goals:**

- Custom OpenSpec schemas or tooling.
- Seeding `openspec/specs/` from `manifest.md` or `architecture.md`. That can
  follow once maintainers have settled the decisions below.

## Decisions

**Default `spec-driven` schema.** Its proposal → specs → design → tasks artifacts
already separate requirements from implementation decisions. Alternative: a custom
schema with an explicit approval artifact, rejected as unnecessary infrastructure.

**One Pull Request per change, gated by a `spec-approved` label.** The proposal is
pushed first, maintainers review it and add the label, and implementation commits
follow in the same Pull Request. Alternative: separate specification and
implementation Pull Requests, which adds overhead and splits the review history.

**Traceability by naming and a proposal line.** Change IDs
`gh-<issue>-<kebab-summary>` plus `Issue: #N` in `proposal.md`, supported by
`openspec/config.yaml` rules and the Pull Request template. Alternative: a GitHub
integration service, rejected as unnecessary infrastructure.

**Pull Requests come from forks; issues do not need one.** This applies to every
contributor, including maintainers, so branches in this repository stay limited to
`main`. Alternative: allow maintainers to use branches here, rejected by the
maintainer in favour of one rule for everyone. The rule is documented and checked
in review. A CI check that fails on same-repository Pull Requests was also
considered, and it can be added later if the rule is missed in practice.
Validation still works on fork Pull Requests, because it needs no secrets and only
reads the repository. GitHub may ask a maintainer to approve the workflow run for a
first-time contributor.

**The archive Pull Request closes the issue.** Specification and implementation
Pull Requests use `Refs #N`, and the archive Pull Request uses `Closes #N`, so an
issue stays open until its specifications are merged into `openspec/specs/`.
Alternative: close the issue when the implementation is merged, rejected because
the archive step could then be forgotten with nothing left open to show it. An
issue delivered through several changes is closed only by the archive Pull Request
that completes the last of them.

**`AGENTS.md` as the single instruction source.** Most coding agents read it
natively, and `CLAUDE.md` points to it. Claude Code gets the native skills and
`/opsx:*` commands first. Other agents can be added with
`openspec init --tools <id>`. Alternative: one full instruction file per agent,
rejected because the copies would drift apart.

**CI installs a pinned, checksum-verified standalone binary.** The workflow
downloads a fixed release and checks its SHA-256 before running it. Alternatives:
the unpinned install script, whose content is not fixed, or `npm install -g`, which
adds a Node toolchain to a repository that does not otherwise need one.

**Project context links to existing documents.** `openspec/config.yaml` summarizes
`manifest.md` and `architecture.md` and links to them. It states that the code they
describe is not in the repository yet, and sets no test or lint rules for it.
Alternative: copying the documents into the context, rejected because the copies
would go out of date.

## Architectural implications

This change adds no runtime component and does not alter the described
architecture. It does expose four conflicts or gaps in the current documents, which
are listed under Open Questions. Until they are decided, the project context names
each difference and tells agents to report it in `design.md` when a change touches
it, rather than picking a side.

## Risks / Trade-offs

- [Anyone with triage rights can add `spec-approved`] → Documented as an open
  governance item, with `CODEOWNERS` and branch protection as recommendations.
- [`architecture.md` describes code that is not in the repository] → The context
  marks it as the target system, so agents must check before assuming code exists.
- [The first implementation issue may hit an undecided conflict] → The open
  questions below are named in the project context, so it surfaces during proposal
  review rather than during coding.
- [The fork rule is not enforced technically, so someone with write access can still
  open a Pull Request from a branch in this repository] → Reviewers check the source
  of the Pull Request, and the template reminds contributors of the rule.
- [Pinned OpenSpec version ages] → The version and checksum are set in one place in
  the workflow.
- [Green CI is not functional correctness] → The contributor guide lists the checks
  that require human review.

## Open Questions

These need a maintainer decision. The recommendations are proposals only, and this
change implements none of them beyond naming them in the project context.

1. **Deployment target.** `manifest.md` section 11 describes a single local
   docker-compose deployment. `architecture.md` is designed for Kubernetes.
   - A: docker-compose for the MVP, Kubernetes as the later target.
   - B: Kubernetes from the start, using a local cluster for development.
   - C: Support both from the first implementation.
   - Recommendation: A, if the MVP definition of done in `manifest.md` still stands.

2. **Connector layout.** `manifest.md` lists separate EDC control and data planes
   per participant. `architecture.md` uses one combined control and data plane per
   participant.
   - A: Combined, as in `architecture.md`.
   - B: Separate, as in `manifest.md`.
   - Recommendation: A, because it means fewer components per participant and matches
     the Technology Stack table.

3. **Which document leads.** The API Gateway, Participant Registry and Keycloak
   appear in `architecture.md` but not in `manifest.md`.
   - A: `architecture.md` leads on design, and `manifest.md` leads on MVP goals and
     definition of done.
   - B: `architecture.md` leads everywhere, and `manifest.md` is historical.
   - C: `manifest.md` leads until the MVP is complete.
   - Recommendation: A.

4. **Duplicate text.** `manifest.md` contains its full content twice; the second copy
   starts on line 458, directly after the end of the first.
   - A: Remove the second copy in a separate documentation change.
   - B: Remove it in this change.
   - C: Leave it.
   - Recommendation: A, to keep this change free of edits to the project documents.
